## 0. 三分钟版本

我们做的事，一句话：

> 把 68 篇论文里的实验数据，变成**一个能查、能改、能审的数据库**。

三个数字先记住：

| 数字 | 含义 |
|---|---|
| 68 篇 | 论文数量（全部是 Fe–Mn–Al–C 系"低密度钢"） |
| 638 个 | 样品数量（一个"成分 + 一套工艺"算一个样品） |
| 1,508 条 | 性能数据（强度、延伸率、硬度……），每条都能定位到论文，其中 75% 能直接跳到原句 |

一个"企业级数据库"要回答五个问题。这个库的每一层，都在回答其中一个：

| 问题 | 这个库的回答 | 靠什么 |
|---|---|---|
| **存得住吗？** | 6,667 个原始对象 + 36 张表，共 332 MB | 资产湖 + 事实源 |
| **查得到吗？** | 5,099 条可检索文档，精确 / 关键词 / 语义三种查法 | 检索层 |
| **改得动吗？** | 人工修订有记录、可撤销、重跑不丢 | 校订层 |
| **说得清吗？** | 68,944 条溯源；75% 能到原句，其余明确标注 | trace + 版本 + 审计 |
| **用得上吗？** | 10 个页面、22 个接口 | 消费层 |

四层结构就是这五件事的物理落点：

```
        ┌─────────────────────────────────────────┐
        │  消费层   网页 / 接口 / 给 AI 用的语料    │  ← 人在这里看
        ├─────────────────────────────────────────┤
        │  检索层   目录：精确 / 关键词 / 按意思     │  ← 帮人找到
        ├─────────────────────────────────────────┤
        │  事实源   表格：一条条可查询的记录         │  ← 数据本体
        ├─────────────────────────────────────────┤
        │  资产湖   保险柜：原始文件 + 指纹，只读    │  ← 证据的根
        └─────────────────────────────────────────┘
```

一句话记住四层：**湖是保险柜，仓是账本，检索层是账本的目录，消费层是柜台。**

为什么不是"一个大 Excel"，也不是"直接把 PDF 丢给 AI"？因为那三件事——**查、改、说**——一个都做不到。
第 3、4 节展开。

## 1. 这个库到底存什么，不存什么

### 1.1 存的是"论文说了什么"，不是"论文"

一条完整记录长这样（真实例子，简化过）：

| 项目 | 内容 |
|---|---|
| 样品 | Fe-28Mn-10Al-0.8C，900 °C 退火 1 小时 |
| 性能 | 抗拉强度 850 MPa，延伸率 62% |
| 出处 | 论文 `10.1016/j.msea.2021.141234`，表 2 第 3 行；正文 3.2 节第 2 段 |
| 由谁抽出 | 2026-10-09 那批，模型 `deepseek-flash`，第 47 篇 |
| 有没有人改过 | 没有；或"张三改过抗拉强度，从 850 改为 845，理由：原文笔误" |

也就是说，这个库存的不是"知识"，而是**声明 + 声明的出处 + 出处的修订史**。
"低密度钢为什么加铝"这类结论，库不负责下；库负责把"谁、在哪篇、哪句、说了什么"原样摆出来。

### 1.2 不存什么

| 不存 | 为什么 | 那它在哪 |
|---|---|---|
| 论文 PDF 原文 | 700 多 MB，是"输入"不是"结果"；而且版权上不适合再分发 | `01_raw/`，需要时按论文编号取 |
| 模型"总结"出来的结论 | 总结会掺入模型自己的判断，不是原文事实 | 只把原文句子存成证据块 |
| 计算出来的性质（比如第一性原理算的弹性模量） | 那是另一类数据，和实验数据混在一起会误导 | 不混入；未来可作为外部关联表接入 |
| 用户的查询记录、浏览行为 | 与科研数据无关 | 不采集 |

### 1.3 三个最基础的词

- **表（table）**：Excel 里的一张 sheet。
- **行（row）**：表里的一条记录，比如"某个样品的一条性能"。
- **列（column）**：表里的一个字段，比如"抗拉强度（MPa）"。

**那为什么不直接用 Excel？** 三个硬理由：

1. **要同时被很多人和程序查**。Excel 一次只能一个人改；网页、脚本、AI 要同时读。
2. **一条性能要能挂 40 多条溯源信息**。1,508 条性能对应 68,944 条溯源记录，Excel 放不下这种"一对多"。
3. **改一处，处处一致**。比如改了一个样品的合金牌号，所有引用它的地方都得跟着变；数据库有"外键"和"事务"来保证这件事，Excel 只能靠人。

这就是"数据库"存在的理由，不是因为它高级，而是因为这三件事 Excel 做不到。

## 2. 四层结构：一层回答一个问题

### 2.1 逐层说人话

**第一层 · 资产湖（Lake）——"保险柜"**

把原始文件（MinerU 解析出的 JSON、论文里的图片）原样放进一个目录，每个文件用它的**内容指纹**命名。
指纹（学名 `sha256`）是把文件内容算成一串 64 位字符：内容变一个字节，指纹就完全不同。

- 回答的问题：**这份原始材料，还是当初那一份吗？**
- 好处：① 谁都改不了（改了指纹就对不上）；② 同样的文件只存一份（68 篇里有重复图片，自动去重）。
- 现在装着：6,667 个文件，148 MB。
- 拿掉它会怎样：数据库里的每个数字都变成"孤证"，没法证明它来自哪份原始文件。

**第二层 · 事实源（PostgreSQL）——"账本"**

把湖里的 JSON 拆成一张张表：论文表、合金表、样品表、性能表、相表、工艺表、图表表……
同时保留一份原文 JSON（叫 `payload`），防止拆表时丢信息。

- 回答的问题：**有哪些样品？成分多少？强度多少？**
- 现在装着：36 张表 + 12 个视图，332 MB。
- 拿掉它会怎样：只剩一堆 JSON 文件，查"铝含量 8–11% 的钢"要写程序遍历所有文件。

**第三层 · 检索层——"目录"**

给账本编索引：按元素、按强度区间、按年份能秒查；还能把一句话变成"意思坐标"，按语义找。

- 回答的问题：**哪些样品和"加铝降密度"有关？**
- 现在装着：5,099 条可检索文档，全部做了语义向量。
- 拿掉它会怎样：只能精确匹配，问"为什么加铝能降密度"会一条都搜不到。

**第四层 · 消费层——"柜台"**

网页（10 个页面）、接口（22 个）、给 AI 用的语料。

- 回答的问题：**我想看某个样品，点哪里？**
- 拿掉它会怎样：数据还在，但只有会写 SQL 的人能用。

### 2.2 原设计 vs 现在：四层都落地了吗

《数据库建立》2026 年 10 月那版文档里，画的就是这四层。逐层对照：

| 层 | 原设计 | 现在实施情况 | 差距 |
|---|---|---|---|
| 消费层 | 查询 API / RAG Agent / 分析看板 / 下游训练数据导出 | 网页 10 页、接口 22 个、语料走检索表、看板 3 张 | **训练数据导出未做** |
| 检索层 | 精确：PG 列 + GIN；语义：pgvector(HNSW)；全文：tsvector（可升级 OpenSearch） | 列索引 + 全文 + 模糊 + 向量（384 维）全做了；中文用 jieba 分词 | OpenSearch 未上（规模没到） |
| 事实源 | PostgreSQL：实体表(列) + JSONB(保真) + trace | 36 表 + 12 视图；原文进 `payload`；溯源 68,944 条 | 无 |
| 资产湖 | 对象存储（MinIO/S3/OSS）：原始 JSON + 图片 | 本地目录 + 内容寻址，写入路径已按 S3 的布局设计 | 后端仍是本地磁盘 |

所以"四层都落地了"这句话是准确的：**真正没做的只有两件**——下游训练数据导出、OpenSearch。
而且这两件性质不同：前者是"还没排期"，后者是"规模还没到，到了再换，不影响其他层"。

### 2.3 为什么湖和仓要分开

一句话：**账本可以重抄，保险柜不能重造。**

- 如果某张表设计错了（比如少了一列），做法是改表结构，然后从湖里把 68 篇**重新灌一遍**，30 秒。
- 如果湖里的原始文件被改了，那就没有任何东西可以对照了——所以湖只允许"新增"，不允许"修改"。

这也是为什么数据库可以随时"删了重建"，而湖必须备份。两者的地位不一样：
**湖是唯一的根，仓是可以再生的枝叶。**

## 3. 为什么要分四层，而不是一层

分层的本质，是**把"变化速度不同的东西"分开**。

| 层 | 多久变一次 | 谁能改 | 坏了怎么办 |
|---|---|---|---|
| 资产湖 | 几乎不变（只增） | 谁都不能改 | 从备份恢复 |
| 事实源 | 每次重跑都可能变 | 只能通过入库程序 | 删库，从湖重放 |
| 检索层 | 换索引/换引擎时变 | 可以整体替换 | 重建索引 |
| 消费层 | 随时加页面、加接口 | 前端随便改 | 不影响下面 |

规则只有一条：**变得快的放上面，变得慢的放下面；上面可以坏，下面不能坏。**

反过来看三个"如果只有一层"的反例，会更清楚：

**反例一：只有一个大 Excel。**
无法多人同时查、无法做语义检索、无法保证 68,944 条溯源和 1,508 条性能对得上。
更致命的是：改错一个单元格，没有任何历史记录。

**反例二：只有一个 MongoDB（文档库），把 JSON 原样存进去。**
看起来省事，但"铝含量 8–11% 且抗拉强度 > 800"这种查询会非常慢；
换一种问法就要加一套索引；而且没有一个"稳定的事实层"供报表和 AI 共用。

**反例三：让 AI 直接读 PDF 回答问题。**
这是最容易被想到的方案，也是最不可控的：同一个问题问两次，答案可能不同；
答错了无法定位；68 篇还能撑住，680 篇就崩了。
**这个库的定位，恰恰是给 AI 提供一个"可引用的、稳定的底座"**——AI 负责组织语言，库负责提供事实和出处。

## 4. 五个问题，五组设施（全文最重要的一节）

第 0 节列了五个问题。这一节说清楚：每个问题对应哪组设施、为什么这么设计、如果没有会怎样。

### 4.1 存得住：湖是保险柜，仓是账本

**问题**：原始文件会不会被改？数据能不能重建？

**做法**：

- **湖**：原始 JSON 和图片按内容指纹（`sha256`）落盘，只增不改；现在 6,667 个对象、148 MB。
- **仓**：36 张表 + 12 个视图；从湖里重灌一遍只要 30 秒。
- **版本**：每条事实带批次号（`run_id`），4 个批次并存；换模型重跑，旧结果不消失。

**为什么这么分**：账本可以重抄，保险柜不能重造。表设计错了，改表 + 从湖重放；
湖被改了，就没有任何东西可以对照了。

**如果没有**：数据库里的每个数字都成了孤证，说不清它来自哪份原始文件。

> PDF 不入湖，但没丢：68 篇 PDF 在 `01_raw/`，按 DOI 命名，约 700 MB。
> 湖只存"派生资产"（解析出的 JSON 与图片），因为 PDF 是输入，不是结果。

### 4.2 查得到：列做筛选，JSONB 保原文

**问题**：1,508 条性能，怎么在两秒内筛出"铝 8–11%、抗拉 > 800"？

**做法**：

- 只把**身份、外键、会被筛选的维度**做成列：`metric`、`value_canonical`、`unit_canonical`、`year`、`family_key`……
- 其余完整原文进 `payload`（JSONB），保真、可回填。
- 建三种索引：普通列索引（精确筛选）、全文（关键词）、向量（按意思）。

**两个真实例子**：

| 原文 | 入库后 | 为什么 |
|---|---|---|
| `"685"` + 单位 `"MPa"` | `value_num = 685`、`unit_canonical = 'MPa'` | 要比较大小、要跨单位换算 |
| `"Bal."`（余量） | 留在 JSONB；另建 `alloy_element` 行，Fe 用 100 − 其他元素推算，标 `is_inferred` | 字符串不能当数字用；推算值必须可识别 |

**如果没有**：只能做字符串匹配——`"1000" < "427"` 是按字典序比的，`WHERE 强度 > 800` 一条都查不出来。

### 4.3 改得动：修改写在"便利贴"上，重跑再贴回去

**问题**：发现模型抄错了一个值，改完之后，下次重跑会不会被冲掉？

**做法**：不直接改表。人工修改写进 `curate.change`（修订记录），每次入库结束后系统自动重放一遍。
修改有前后值、有理由、可撤销。

**为什么**：直接 `UPDATE` 表里的值，下次 `ingest` 会把整篇删掉重写，修改就没了——实测发生过。

**如果没有**：要么不敢改，要么改完提心吊胆。

### 4.4 说得清：每个值挂出处，每次修改留记录

**问题**：这个 850 MPa 是哪来的？上个月的值为什么和现在不一样？谁改的？

**做法**：

- **溯源**：每个值旁边存一条指针，指向原文的段落/表格（`sample_trace`，68,944 条）。
- **版本**：`run_id` + `is_latest`，4 个批次并存，能看历史。
- **审计**：修改记前后值、理由、操作人。

**这里要说清一件事**：机器读论文确实会出错——漏字段、串行、把"约 350–450"补成"400"。
但这不是"数据不可信"，而是"文献数据必须可举证"：就像财务系统保留凭证，不是因为会计会做假账，
而是因为每一笔都要能查。做法是把风险变成可控的三道防线：

1. **入库前**：95 项测试 + 12 条质量规则，`error` 级 0 条；
2. **入库时**：每个值尽量挂出处（75% 到段落），挂不上的**明确标注"弱溯源"**，不假装；
3. **入库后**：发现问题可以改（4.3）、可以重放、可以回到原始文件（4.1）。

**如果没有**：审稿人问"这个数哪来的"，只能回答"模型说的"。

### 4.5 用得上：界面、接口、语料

**问题**：不会写 SQL 的人怎么用？

**做法**：10 个页面（总览、样品库、成分检索、文献、检索、趋势、质量…）、22 个接口、可导出的语料。

**还没做**：下游训练数据导出（第 10 节）。

### 4.6 五个问题，四层设施

| 问题 | 主要落在 |
|---|---|
| 存得住 | 资产湖 + 事实源 + 版本 |
| 查得到 | 检索层（列 / 全文 / 向量） |
| 改得动 | 校订层 |
| 说得清 | trace + 版本 + 审计 |
| 用得上 | 消费层 |

所以四层不是审美选择：**压成两层，丢的不是两张表，而是溯源、版本、修订、重放这四样能力。**

## 5. 数据是怎么进来的：从 PDF 到一行记录

### 5.1 三步流水线

```
论文 PDF
   │  ① MinerU（版面解析工具）
   ▼
文字 + 表格 + 图片 + 版面坐标        → 01_raw/（68 篇，960 MB）
   │  ② 大模型抽取
   ▼
结构化 JSON（成分、工艺、性能、相…）  → 02_extraction/（68 篇，69 MB）
   │  ③ 入库程序（ETL）
   ▼
数据库表 + 湖里的原始文件             → 05_lake/ + PostgreSQL
```

每一步都可能出错，所以每一步的产物都**原样保留**：
出了问题可以只重跑第 ③ 步（30 秒），不必重新解析 PDF，也不必重新调用模型（那要花钱和时间）。

### 5.2 三条工程规则

**规则一：一篇论文，要么整篇进，要么整篇不进（事务）。**
像银行转账：不能出现"钱扣了但没到账"。入库时先删掉这篇的旧数据，再按顺序写入；
中间任何一步失败，全部回滚，这篇保持原样，其他篇继续。

**规则二：同一篇重复入库，结果一样（幂等）。**
像"重新打印一份文件"：打一次和打十次，拿到的东西相同。
所以运维不需要"先清库再入库"，直接重跑就行。

**规则三：只读"定稿"，不读"草稿"。**
提取目录里有两类东西：`output/`（当前定稿）和 `_monitor/`（过程日志，1.1 GB，只增不改）。
入库只读 `output/`。把过程日志也入库，等于把草稿当定稿，越跑越乱。

### 5.3 每件产物去了哪张表

| 提取产物 | 入库位置 | 数量 |
|---|---|---|
| `evidence_blocks.json`（原文切块） | `core.evidence_block` | 10,316 块 |
| `discover/*.json`（论文级信息） | `core.paper` + `payload` | 68 篇 |
| `sample/*.json`（样品级信息） | `core.sample` / `alloy` / `phase` / `property_value` | 638 样品 |
| `sample_trace/*.json`（每个值的出处） | `core.sample_trace` | 68,944 条 |
| `figure/*.json`（图、表、观察项） | `core.figure` / `figure_observation` | 1,041 / 12,405 |
| `image_groups.json`（图表与题注的对应） | `core.figure` 的题注与引用 | 用于对齐证据 id |
| `multimodal_evidence_index.json` | **不建表**（与上一项 90% 重复），只留档 | — |

**"48 个表/视图是怎么长出来的"**，答案就是这张表：不是先设计 48 个表/视图再找数据，
而是**先看手里有什么产物，再决定每件产物落到哪**。

## 6. 表为什么长这样：六个决定

### 6.1 主键用"论文号 + 样品号"，不用自增编号

**主键**就是"这条记录的唯一身份证"。

- 自增编号 = 座位号：1 号、2 号、3 号。换一个场地（换一个库），座位号全变。
- 业务编号 = 身份证号：`论文A + 样品3`。走到哪都是它。

好处：重跑、迁移、合并库时不会串号；坏处：写起来长一点，多表关联时多带一列。
我们选身份证号，因为**数据要长期活着，编号必须稳定**。

### 6.2 一个"样品" = 成分 × 工艺，工艺单独一张表

同一炉钢，900 °C 退火和 1000 °C 退火，性能完全不同——所以它们是**两个样品**。
如果只按成分建一条记录，就会把两种性能混在一起。

工艺也不塞进样品表的一个字段里，而是单独一张"工艺步骤"表（2,610 行），因为工艺是**一串步骤**：
熔炼 → 热轧 → 冷轧 → 退火。拆成表之后，才能问"退火温度 900 以上的样品，强度分布如何"。

### 6.3 性能用"长表"：一行一个值，不是一行一个样品

- **宽表**：一行一个样品，列是"抗拉强度、屈服强度、延伸率、硬度、密度……"，几百列。
- **长表**：一行一个值，列是"哪个样品、哪个性能、多少、什么单位"。

为什么选长表？68 篇论文里出现的性能种类不一样：有的测了 3 种，有的测了 15 种。
用宽表会有几百列、90% 是空的；加一种新性能还要改表结构。长表加性能只是多几行。

代价：查"一个样品的全部性能"要把多行拼起来（叫"透视"），SQL 写起来长一点。
但这是**一次写、无数次查**的买卖，值得。

### 6.4 什么进"列"，什么进"JSONB"：衣柜原则

- **列** = 挂在外面的衣服：经常穿（经常用来筛选、排序、关联）。
- **JSONB** = 装箱的衣服：换季的、不常穿的，但一件都不能扔。

具体规则：**只有身份、外键、会被 `WHERE` 用到的维度才做成列**（强度、温度、年份、元素……）；
其余完整原文一律进 `payload`（一个 JSONB 字段，存的是原始 JSON 的全文）。

为什么不全做成列？因为那会变成"几百列、大部分为空"的表，改一次结构要动全库。
为什么不全塞 JSONB？因为 JSONB 里的数值比较慢，而且没有类型检查。

`payload` 还有一个隐藏作用：**它是"后悔药"**。哪天发现少拆了一个字段，可以从 `payload` 里补出来，不用重新跑模型。

**四个真实例子**（都来自这个库）：

| 内容 | 进哪 | 为什么 |
|---|---|---|
| 论文 DOI、年份、期刊 | 列 | DOI 要唯一，年份要排序，期刊要分组 |
| 性能值 `"685"` + 单位 `"MPa"` | 列（`value_num` / `unit_canonical`） | 要比较大小、要跨单位换算 |
| 成分原文 `"Bal."` | JSONB 原文 + 另建 `alloy_element` 行 | 原文是字符串，硬转数字就错了 |
| 试验条件（温度、应变速率、试样尺寸…） | JSONB | 目前没有查询按它过滤；哪天要按温度筛，再提升为列 |
| 样品的界面、缺陷交互、应力-应变曲线描述 | JSONB | 结构每篇不同、层数深、从不用于筛选 |

一条经验规则：**先放进 `payload`，等它第二次出现在 `WHERE` 里，再提升为列。**

### 6.5 事实与出处分成两张表：正文与脚注

`core.sample_data` 存"值"，`core.sample_trace` 存"这个值出自哪"。
两张表用"论文号 + 样品号 + 路径"对上，路径精确到 JSON 里的第几个字段（叫 JSON Pointer）。

为什么不放一张表？因为一条事实可能对应多条证据（一句话 + 一张图），
放一起会重复存事实；而且重跑时"值"会变，"出处"不该跟着变。

### 6.6 "同一合金"不强行合并：两级身份

68 篇论文里，"铁素体"有 30 多种写法：α、delta ferrite、bcc ferrite、δ-Fe……
如果系统自作主张把它们合并成一个，一旦合并错，错误会扩散到所有统计里，而且很难发现。

所以现在只做两级：

- **论文内**：用"论文号 + 样品号"唯一标识，绝不跨论文合并；
- **跨论文**：提供一张"标准词表"（20 条合金族规则、40 个常见相），
  能对上就挂一个"族"的标签，对不上就留空（250 个合金里 7 个仍"未分类"）。

**留空不是失败，是诚实。** 等数据多了、规则稳了，再回头补。

### 6.7 表与表怎么连：38 条外键 + 一种软连接

"外键"就是引用另一张表的身份证：`core.sample.paper_id` 只能填 `core.paper` 里真实存在的论文号。

主键是复合的 `(paper_id, sample_id)`，因为 `sample_1` 这种编号只在**一篇论文内部**唯一，
68 篇里每篇都有一个 `sample_1`。所以这个库的 join 几乎都带着 `paper_id`。

一条主线：

```
paper（论文）
├── alloy（合金）── alloy_element（成分，一个元素一行）
├── sample（样品 = 合金 × 工艺）
│   ├── property_value（性能）    ├── phase（相）
│   ├── processing_step（工艺）   ├── sample_data（原文 JSON）
│   └── sample_trace（出处）──────┐
├── evidence_block（原文切块）◀───┘ 数组软连接
└── figure（图/表）── figure_observation（观察项）
```

有一类连接没法用外键：`sample_trace.block_ids` 是一个数组，指向 `evidence_block`。
数组做不了外键，所以靠 GIN 索引加速 + 一条测试逐条验证（68,944 条指针 100% 命中）。

### 6.8 视图：拼好的查询，不占空间

视图不是表，**它是一条存起来的 SQL**。查它的时候才去算。

比如 `api.sample` 一次拼了 5 张表（样品、合金、论文、工艺、合金族），
界面、接口、导出脚本都只写 `select * from api.sample`，不用各写一遍 join。

这个库有 12 个视图：10 个给界面和接口，2 个给校订层。
它们没有自己的索引，每次查询现算；638 个样品这个量级，足够快。

## 7. 检索：三种问法，三种索引

### 7.1 索引是什么

一本书 500 页，找"马氏体"这个词：没有索引只能一页页翻（数据库里叫"全表扫描"）；
有索引，翻到"马"字部，直接跳到第 217 页。

数据库索引就是这本书的目录。代价是：**目录本身要占地方，而且每次改内容都要更新目录**。

### 7.2 三种问法，三套目录

| 你想问的 | 例子 | 用什么 |
|---|---|---|
| 精确条件 | 铝含量 8–11%，抗拉强度 > 800 | 普通列索引 |
| 某个词 | "TWIP"、"κ-碳化物" | 全文索引 |
| 一个意思 | "为什么加铝能降密度" | 语义（向量）检索 |

**向量检索**用大白话说：把一句话变成 384 个数字（像地图上的坐标）。
意思相近的句子，坐标也相近。所以"加铝降密度"能找出一段写着"Al 降低钢的密度"的原文，
即使两句话一个字都不重合。

**三种结果怎么合并？** 用"名次相加"（学名 RRF）：全文检索排第 1、语义排第 5、模糊排第 9，
综合名次就是 1+5+9。不比"分数"，只比"名次"——因为三种打分方式的分数量纲根本没法比。

### 7.3 中文是个额外的坑

PostgreSQL 原生不认识中文词，只会按空格切。所以入库时先用 jieba 把中文切成词（"低密度钢"→"低 密度 钢"），
查询时用同一套规则切。**切法必须一致**，否则索引和查询对不上，等于白建。

### 7.4 成分检索：两个必须处理的坑

研究者的真实入口是"给我一个 Fe-28Mn-10Al-0.8C 附近的钢"，不是关键词。

但原始数据里，铁（Fe）经常写成 `Bal.`（余量），没有具体数字。250 个合金里：

- 只有 **4 个**给了 Fe 的具体数字；
- **149 个**写 `Bal.` / `balance` / `余量`；
- **32 个**有 Fe 行但值为空或 `x (variable)`；
- **65 个**根本没列 Fe（只列了合金元素）。

如果严格按"Fe 有数字"来匹配，250 个合金里只剩 4 个能用。

处理办法：**用 100 减去其他元素，推算出余量，并打上星号标记**（`is_inferred`）。
展示时写"Fe 61.2*"，星号表示"这是推算的，不是原文"。
推断之后，243 个 Fe 基合金都能按 Fe 含量筛（4 条原值 + 239 条推断值）。

查询时先找完全匹配的；找不到，按"离你给的区间有多远"排序，返回最接近的几个，
并告诉你差在哪（"Al 低了 7.4 个百分点"）。**宁可告诉你没有，也不假装有。**

## 8. 为什么选 PostgreSQL

选型的原则不是"选最强的"，而是**选"最少拼装"的**：每多引入一个组件，就多一套备份、权限、监控和故障模式。

| 候选 | 擅长 | 在这批数据上的问题 | 结论 |
|---|---|---|---|
| MySQL | 轻、生态广 | JSON 字段没有专用索引，没有向量检索，窗口函数弱 | 不用 |
| MongoDB | 原样存嵌套 JSON | 跨样品聚合、区间比较、多表关联都弱 | 用 JSONB 拿它 80% 的好处 |
| Neo4j | 图关系（溯源链、工艺链） | 68,944 条溯源用三列就能存，不值得多一个库 | 不用 |
| Elasticsearch | 中文分词、模糊、聚合 | 数值过滤和事务要回 PostgreSQL，一致性靠补偿 | 暂不用 |
| 专用向量库 | 向量检索快 | 又要多一套库，且和事实数据分离 | 不用（用 pgvector） |
| **PostgreSQL** | 表格 + JSON + 全文 + 向量 + 事务，一个库全有 | 单机、要自己运维 | **选它** |

一句话：**这批数据的四种需求（精确筛选、JSON 保真、中文检索、语义检索），PostgreSQL 一个库全包了。**
少一个组件，就少一类半夜出问题的可能。

代价也要说清楚：它是单机数据库，没有"分布式"能力；向量索引占内存；
数据量到千万级时，检索要外迁。这些在第 10 节展开。

## 9. 这套设计的账单

任何设计都有代价，摊开来看：

| 代价 | 具体数字 | 值不值 |
|---|---|---|
| 行数放大 | 1,508 条事实 → 68,944 条溯源（约 45 倍），溯源表 55 MB | 值：溯源是这套库的立身之本 |
| 数据库体积 | 332 MB（含索引） | 值：一部高清电影的零头 |
| 表很多 | 36 张表 + 12 个视图 | 值：每张表对应一类明确的问题；代价是新人要一周熟悉 |
| 入库慢一点 | 68 篇约 30 秒（单机） | 值：换来"整篇可重放" |
| 不能直接改表 | 必须走校订层 | 值：换来"修改不会被重跑冲掉"；代价是多一步操作 |
| 定性值不能比较 | 172 条（11%） | 诚实：不硬凑数字，查询时单独筛 |
| 一个人维护 | 迁移、备份、监控都要人 | 现阶段可接受；上生产要加值守 |

按现在的量推算：1 万篇论文时，湖约 20 GB、库约 40 GB、全量入库约 75 分钟（并行可压到 12 分钟）。
**这套架构撑到 1 万篇没问题，撑到百万篇要换检索层。**

## 10. 边界：什么没做，什么不该做，什么时候该换

### 10.1 没做的（诚实清单）

| 没做 | 影响 | 什么时候需要 |
|---|---|---|
| 下游训练数据导出 | 想把库里的数据拿去训练模型，目前要自己写 SQL 导 | 有模型训练需求时（工作量约 1 周） |
| OpenSearch | 检索量大了会慢；现在 5,099 条文档完全够用 | 检索文档到百万级 |
| 多用户权限 | 现在所有接口只读、无登录；校订接口有开关 | 多人协作、对外提供服务时 |
| 备份演练 | 有备份脚本，但没有定期"恢复演练" | 上生产前必须做 |
| 跨库联邦 | 不能直接查 Materials Project 等其他库 | 需要联合检索时 |

### 10.2 不该做的（会破坏架构）

1. **不要直接 `UPDATE` 表里的数据**——下次入库会被覆盖，而且没有审计记录。走校订接口。
2. **不要把 PDF 放进湖**——湖只存"派生资产"，PDF 是输入，放进去会让湖膨胀 5 倍且无法去重。
3. **不要自动合并相名/合金名**——合并错一次，污染所有统计，且难以追溯。
4. **不要把 `_monitor/` 入库**——那是过程日志，不是事实。

### 10.3 什么时候该换架构

- 论文到 10 万篇以上 → 检索层外迁（OpenSearch / 向量库），事实层不动；
- 多个团队同时写 → 加权限、审计、可能拆库；
- 需要实时更新（分钟级）→ 现在的"整篇重灌"模式要改成增量；
- 需要和外部大库联合查询 → 加一层"联邦查询"，不改内核。

## 11. 和别的材料库差在哪

Materials Project（美国）、NOMAD（欧洲）、ICSD（晶体结构）都是优秀的材料库，但它们是**"结果库"**：
存的是计算或实验得到的**最终结果**，一条记录就是一个材料。

我们这个库是**"声明库"**：

| | 结果库（MP / NOMAD / ICSD） | 这个库 |
|---|---|---|
| 一条记录是什么 | 一个材料/结构 | 一篇论文里的一个声明 |
| 数据从哪来 | 计算流程 / 实验测量 | 从文字里读出来的 |
| 错了怎么办 | 重算 | 回到原句，人工修订，重放 |
| 版本 | 整体发布 | 每个值带批次，可追溯 |
| 核心价值 | 数据全、算得准 | **可引用、可复核、可修订** |

一句话：**他们在记录"结果"，我们在记录"谁在哪儿说了什么，以及后来谁改了它"。**

两者不冲突：将来完全可以把 MP 的计算值作为"外部关联表"接进来，
和文献里的实验值并排展示——但绝不混成一条记录。

## 12. 名词小词典

| 词 | 一句话解释 |
|---|---|
| 数据库 | 能同时被很多人和程序查询、并且保证数据一致的数据仓库 |
| 表 / 行 / 列 | 一张 sheet / 一条记录 / 一个字段 |
| 主键 | 一条记录的唯一身份证 |
| 外键 | 引用另一张表"身份证"的字段，用来保证两边对得上 |
| 索引 | 书的目录，让查询不用逐页翻 |
| 事务 | 一组操作要么全成功、要么全失败（像转账） |
| 幂等 | 同一操作做一次和做十次，结果一样 |
| 迁移（migration） | 给已建好的库改结构，一次一个脚本，按顺序执行，旧脚本不能改 |
| schema | 库里的分区，比如 core（事实）、ops（运维）、lake（湖）、canon（词表） |
| 视图（view） | 保存好的查询，像"常用报表模板"，不占数据空间 |
| JSON / JSONB | 一种"可以嵌套"的数据格式；JSONB 是它的二进制版，能建索引 |
| payload | 存原始 JSON 全文的字段，保真用 |
| ETL | 抽取 → 转换 → 装载，把原料搬进库的三道工序 |
| 哈希 / 指纹 | 把文件内容算成一串固定长度的字符，内容变一点，结果全变 |
| 内容寻址 | 用"内容指纹"当文件名，天然防篡改、天然去重 |
| 全文检索 | 按词找文档，像书末的关键词索引 |
| 向量 / 嵌入 | 把一句话变成几百个数字的坐标，意思近的坐标近 |
| RRF | 把几路检索结果的"名次"相加来排序，避免比较不可比的分数 |
| 物化视图 | 提前算好、存下来的查询结果，读得快但要及时刷新 |
| 溯源（provenance） | 每个数据点"从哪来"的完整证据链 |
| 校订（curate） | 人工修正，单独存一层，重跑后自动重放 |
| run / 批次 | 一次批量抽取任务；同一篇可以有多个批次的结果并存 |
| API / 接口 | 程序之间说话的窗口，比如"给我 Al 8–11% 的样品" |
| 门禁（QA gate） | 自动检查，不通过就不许发布 |

## 13. 常见问题

**Q1：为什么不直接把 68 篇 PDF 丢给 AI，让它回答？**
能回答，但三个问题无解：同一个问题两次答案不同；答错了指不出原文；68 篇还行，680 篇就撑不住。
这个库的作用就是给 AI 一个"可引用的底座"。

**Q2：数据错了怎么办？**
三步：① 页面上点进样品，看原文段落；② 在"人工校订"里改，填理由；③ 系统记录前后值，重跑时自动重放。
全流程有审计，可撤销。

**Q3：换了更好的模型，要重建吗？**
不用重建，直接再灌一个批次（run）。新旧并存，可以对比。旧的仍然可查。

**Q4：为什么库里有 172 条数据"不能比较大小"？**
因为原文就是"随铝含量增加而上升"这种定性描述。硬把它变成数字是造假，所以单独标记。

**Q5：为什么有的数字旁边有星号？**
星号表示"这是推算的"（比如 Fe 余量 = 100 − 其他元素），不是原文直接写的。引用时要说明。

**Q6：能撑多少数据？**
现在 68 篇、332 MB。按线性推算，1 万篇约 40 GB、入库 75 分钟。
检索层到百万级文档时需要换引擎，其他层不用动。

**Q7：这套东西的核心竞争力是什么？**
不是"数据多"，是"能查、能改、能审"：每个数字能定位到论文（75% 能到原句），
改过之后还回得去，重跑也冲不掉。在文献数据里，**可复核**比**多**更难，也更值钱。

**Q8：如果只记一句话，记哪句？**
**湖是保险柜，仓是账本；账本可以重抄，保险柜不能重造。**
